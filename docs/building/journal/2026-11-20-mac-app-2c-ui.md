# Mac app 2c-ui: the dashboard's Mac screens

Phase 2c of the Mac app, dashboard slice. The approved mockup (2026-11-20,
sections 3, 4, 5, 9, 10) is built in `ui/` against bridge v2 and its
amendments; the app side is slice 2c-app in `desktop/`.

## What was decided

- **One module reads the bridge.** `ui/src/desktop.ts` holds the types,
  `desktop` (null in a browser) and the small helpers. Every Mac screen is
  behind `desktop`, so the browser dashboard is unchanged; the click-through
  compares the browser pages with the previous bundle pixel for pixel at
  three widths (web fonts blocked and the caret hidden on both, since both
  vary between two loads of the same bundle).
- **Files become paths, queued at the layout.** Drops on the window and
  `onOpenFile` from the Dock go to a queue in `Layout`, which opens
  Transcribe; the page starts them one at a time and names any that wait.
  Browse uses the same `pathForFile`, so nothing is uploaded or copied.
- **Questions are marked on an answer, not on a close.** The old-launcher
  question and the Terminal card call `firstLaunch.mark` when the person
  answers; Escape hides them for this launch only. New people get Terminal
  as the wizard's optional last step after Finish saved; people who finished
  setup get it once as "One more option".
- **`addToPath` only from the card that shows the line.** The Settings row's
  "Add it for me" opens that card; the card's own button is the yes.
- **The removal result survives the reload it causes.** Bridge v2
  amendment 2: removing the old launcher pauses the app's engine, so the
  dashboard reloads in the middle of `remove()`. The page notes when it
  started a removal; after the reload `App` shows `lastRemoval` from
  `oldLauncher.status()` once, and only when it is newer than that note.
- **Restart engine waits for transcriptions** using `GET /api/jobs` (pending
  and running). If the list can't be read, the button stays available and
  the app's own refusal (bridge v1) says why.

## What the mockup could not have

A real drag does not expose the file's name or size before the drop
(Chromium's protected drag mode; `checks/drag_probe.py` shows `files: 0`
on dragenter and dragover, the file only on drop). The overlay shows the
name and size only when the browser gives them, which in the app is never.

The bridge has no way to copy the engine's log from the dashboard, so the
keeps-stopping banner names the log file instead of promising that Copy
details includes it.

`docs/reviews/2026-11-20-mac-app-2c-ui/proof.md`: the click-through

## Round 1 (review: both NOT YET)

The real app reloads the dashboard to `/` every time the engine returns to
running, and the round-0 stub did not, so the outage banner, the Up next
queue and the removal note had never been tested across that reload. The
stub now reloads as `main.js` does; before any fix, 5 checks failed against
it (`checks/run-r1-stub-before-fixes.out`). Each piece of state that must
outlive a restart now goes to storage before the reload can happen (see
architecture.md, "The reload after every restart"). Other round 1 decisions:
each first-launch question is asked once (Escape and a click outside are the
quiet answer); "ready in Terminal" only when the login shell confirmed it;
Browse fills the box as in the browser (the spec's "submits" was an error).

## Round 2 (review: NOT YET and CONDITIONAL)

Round 1 still let the page guess what the app had done from side signals:
any status other than running meant "the removal ran", any answer to a POST
meant "the file is handled", a stored note meant "this restart is mine".
Round 2 reads facts only. A queued file leaves only once the engine accepted
it and starts only while the engine reads running; the error screen is the
pause. The removal note is resolved against the app's own saved
`lastRemoval`, only while the engine reads running. "Mine" is true only
while the page's own call is in flight. The stub now behaves as the real
bridge by default (sessionStorage as the app's memory, localStorage as its
disk, removal restarts and reloads, `/api` fails while the engine is down);
simplified component cases are labelled "[component]" in the checker.

Documented limits (not built):
- A crash during the job check of his own Restart or Remove click (one HTTP
  read long) shows the asked-for wording and records no outage, once.
- A window reopened while his own restart runs may read it as a crash.
- Files waiting in Up next are lost if anyscribe quits before they start.
- Real Electron reload timing and sessionStorage across `loadURL`: no stub
  proves them; they stay a check on a Mac.

## Round 3 (review: NOT YET and CONDITIONAL)

Two gaps in round 2's design, closed by two rules:
- **A doomed page starts nothing new.** Every return to running reloads the
  dashboard, so a page that has seen the engine leave running will be
  replaced. Without the flag, the old page could start a waiting file just
  before its reload, so the file ran twice or ran unseen. The flag has two
  readers only: the queue start and the startup recovery claim.
- **An async callback acts only on the state it started from.** The removal
  note is read once at page load. Startup recovery resolves only that note,
  so a slow recovery read can no longer clear the note of a Remove clicked
  meanwhile.

Also: the cleanup checklist shows the bridge's reason; files waiting for the
engine are named in the idle, completed and cancelled views; the stub's
removal now settles after "running", with the reload 300 ms later.

Documented limits (not built):
- A crash during a queued file's POST can run that file twice.
- A click on a doomed page in the instant before its reload.
- A removal result is lost if anyscribe quits before a page claims it
  (`lastRemoval` is in the app's memory only).
- A second Remove overwrites an unclaimed note.
- Real Electron timing stays a check on a Mac.

## Round 4 (review: both GOOD TO GO)

Both roles cleared round 3's fixes. The fit review's four nits were fixed by
the lead: the partial-cleanup card shows only what the bridge adds after its own
"Cleanup didn't finish" sentence, below the advice; Up next under a running job
or an error says it waits for the engine while the engine is down; a full stop
goes before "It is running again now."; and the checker's removal reasons now
use the bridge's real wordings. Round 5, the review cap, re-checks only that
change.

## Round 5 (the cap) and close

Round 5 re-checked only the lead's change and found one sentence that
overpromised: with a failed dropped file still first in line, the waiting file
starts after that one is tried again, not as soon as the engine is back. Fixed
by the lead with a check that follows the case through recovery. The review
closed GOOD TO GO; what only a Mac can show is listed in the review log.
