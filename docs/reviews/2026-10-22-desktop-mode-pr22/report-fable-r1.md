FIT REVIEW, PR #22 feat/desktop-mode at 24a5322 (read-only; nothing written, started, stopped or toggled)

1. VERDICT: NOT YET. The job is the right one and the instrument is right (plain OS files built on the user's machine, no signing, no money, no new dependency; Claude Code untouched). Two paths a real user hits early break the owner's first rule ("never has to know about a server, a tray, a login item") and the docs claim recovery the code does not deliver. Both are small fixes in core/desktop.py plus doc wording. CI green on the SHA is a lead claim I did not re-check; the verdict is also conditional on it.

2. FINDINGS (most severe first)

F1. should-fix (fit-blocker for the "click the app" job). CONFIRMED by trace. Where: src/anyscribe/core/desktop.py:156-168 (open_dashboard), src/anyscribe/cli/tray_cmd.py:147-201 (the tray never watches its server child), ui/src/components/Layout.tsx:110-121 (the dashboard's Shutdown button), docs/user/getting-started.md:284.
Scenario: desktop mode installed, tray alive. The user clicks Shutdown in the dashboard sidebar (the doc tells him to, line 110 and 282). The server exits; the tray stays up with "Status: stopped" (nothing in _run_tray polls the child). He later clicks the anyscribe app. open_dashboard: health false, port free, tray.read_pidfile() is a live pid, so _start(None, port, 15) waits 15 s for a tray that is starting nothing, returns "timeout", raises StartFailed. From Finder there is no terminal: the click does nothing for 15 s, the error lands only in ~/.anyscribe/logs/tray.log. The only ways out are tray menu "Restart server" or Quit then click: both are tray concepts the owner said users must never need. Same after any server crash (the spec parks "tray restarting a crashed server", which is fine, but desktop open must then cope). The doc at getting-started.md:284 says "Closed the tab, clicked Shutdown, or rebooted? ... click the anyscribe app if you're in desktop mode": that is exactly the path that fails. No test covers "pidfile alive, server never comes" (test_open_does_not_spawn_second_tray feeds health [False, True]).
Fix (code, smallest): in open_dashboard, when tray.read_pidfile() is alive but port_responding(port) is False after a short grace (3 s, not 15), treat the tray as orphaned: tray.stop_tray(port) then spawn tray_args (on macOS, if service.is_installed(), prefer subprocess launchctl kickstart -k gui/<uid>/com.anyscribe.tray so launchd keeps ownership; else spawn). Add a test: pidfile alive, health always False until the spawn happens; assert stop_tray called and one tray spawned; mutation: remove the orphan branch and the test must time out to StartFailed.
Fix (doc, if code is deferred): getting-started.md:110 and :282, after "click Shutdown in the sidebar", add: "In desktop mode, Shutdown stops only the server; use Quit in the tray icon's menu instead, otherwise the app icon cannot restart it." And rewrite :284 so it does not promise the app icon recovers from Shutdown. Prefer the code fix; the doc fix teaches him the tray.

F2. should-fix. PLAUSIBLE (traced in code, not run; the lead's live test skipped this path by killing the stray 0.17.1 tray by pid first). Where: src/anyscribe/core/desktop.py:180-199, src/anyscribe/core/service.py:174-186 and :170, docs/user/getting-started.md:263-264 ("Upgraded anyscribe with pip? ... this restarts it on the new one"), CHANGELOG.md 0.18.0 "Upgrading" paragraph ("Running it replaces the old login item with the fixed one").
Scenario: the upgrade every existing tray user takes, including the owner: 0.17.x with install-service on, launchd tray running (pidfile present), pip upgrade to 0.18.0, run anyscribe desktop install. No manifest, so no stop_tray. On darwin service.is_installed() is True, uninstall_service() sees a live pidfile and skips launchctl unload (by design, F-settled), only unlinks the file. install_service writes the new plist and runs launchctl load on a job that is still loaded: launchctl prints "Load failed: 5: Input/output error / Try running launchctl bootstrap as root for richer errors" straight onto the user's terminal (_launchctl does not capture output; this exact text is in ~/.anyscribe/logs/tray.log on this Mac from the lead's run). RunAtLoad never fires. open_dashboard(expect_external=True) sees the old pidfile, health true, opens the browser onto the OLD 0.17.1 server. Manifest is written as 0.18.0; desktop status says healthy. Until logout the running tray is the old code on the old plist (no PATH fix, no ProcessType Interactive), so the "ffmpeg missing from the app" bug the release fixes is still live on that machine, while two docs say it was restarted and fixed. Ledger (Task 5d) already names this as "Future fix: install stops the pidfile's tray when no manifest exists"; it should be in this PR because it is the owner's own first-run path.
Fix: in desktop.install, replace `if old:` with: if old or tray.read_pidfile() is not None: tray.stop_tray(old["port"] if old else port); service.uninstall_service(); wait for the port. Also make _launchctl capture output (capture_output=True) and surface a plain sentence only on non-zero exit. Test: no manifest, pidfile alive, is_installed True; assert stop_tray called before uninstall_service before install_service; mutation: drop the pidfile clause and the test fails.

F3. should-fix (doc). CONFIRMED. Where: docs/user/getting-started.md:92-110 (Step 2, Option A).
Scenario: a user runs the one-line installer, which now ends by opening the dashboard with the setup wizard. The guide's very next step tells him to run `anyscribe ui`. If he does, anyscribe ui finds 8457 busy and rolls forward to 8458 (cli/main.py:250), so he now has two servers and two tabs, and the Option A closing line tells him to stop "the server" with Ctrl+C or Shutdown (see F1).
Fix wording, insert at the top of Option A: "**Used the one-line installer?** The dashboard is already open in your browser with the setup wizard; skip the command below and go straight to step 1. Run `anyscribe ui` only in CLI mode (installer with `--no-desktop`, or plain pip)." And change line 110 to: "Close the tab when you're finished. In CLI mode, stop the server with Ctrl+C in the terminal or **Shutdown** in the sidebar; in desktop mode leave it running (Quit from the tray icon stops it)."

F4. nit. CONFIRMED. Where: src/anyscribe/core/desktop.py:159-162 (open after Quit spawns a tray outside launchd), docs/user/commands.md "macOS" blockquote ("If the tray crashes, macOS restarts it ... from the moment you install").
Scenario: macOS, user Quits from the tray (launchd shows `- 0`, job still loaded), later clicks the app. open_dashboard spawns `python -m anyscribe tray` itself, outside launchd, so until the next logout there is no crash restart and launchd's RunAtLoad at next login hits the "already running" exit 0 (harmless). The doc's crash-restart promise is true only for launchd-started trays. The lead already recovered this Mac with `launchctl kickstart -k`, which is the one-line instrument that keeps the promise. Fix: on darwin, if service.is_installed(), run `launchctl kickstart -k gui/<uid>/com.anyscribe.tray` instead of spawning; fall back to spawn if that fails. Or soften the doc: "restarts it after a crash while it is running from the login item (after you Quit and click the app, the next login puts it back under that guard)".

F5. nit. CONFIRMED (live plist on this Mac). Where: src/anyscribe/core/service.py:59-73 (service_path), written into ~/Library/LaunchAgents/com.anyscribe.tray.plist.
The plist bakes the installing shell's entire PATH (on this Mac: .antigravity-ide, .opencode, .bun, nvm, both Python frameworks, and more). It works, and is the simplest thing, but it freezes a snapshot of unrelated tool paths into a login item the user never sees, and a later `anyscribe desktop install` from a different shell (Finder-launched, minimal PATH) silently shrinks it. Acceptable as shipped; if touched, keep only entries that exist at install time, or document in troubleshooting that the saved PATH is "your terminal's PATH at install time" (it already says "a copy of your PATH"; fine).

F6. nit. CONFIRMED. Where: src/anyscribe/cli/desktop_cmd.py:82 prints "Starts at login: /Users/.../Library/LaunchAgents/com.anyscribe.tray.plist"; :22 help says "menu-bar tray" on every OS; ui/src/pages/SettingsPage.tsx:342 caption lists all three OS names to a user on one OS.
A semi-technical user is shown a plist path and a macOS word on Windows. Fix: print "Starts at login: yes" in human mode (keep the path in --json), help "app icon, start at login, tray icon", caption "Starts anyscribe in the menu bar when you log in." on macOS and "... system tray ..." elsewhere (the API already knows the platform; or keep one line: "Starts anyscribe in the background when you log in.").

F7. nit. PLAUSIBLE. Where: install.sh default path on a headless Linux box (desktop.py:162-166 fallback).
`curl | bash` on a server with no display now leaves a detached `anyscribe ui --no-open` running after the installer exits, and webbrowser.open may launch a text browser (lynx/w3m) inside the installer's terminal. Previously the installer was passive by default. Documented opt-out exists (--no-desktop). If install.sh can detect no DISPLAY/WAYLAND_DISPLAY on Linux, skip desktop mode with the same "Desktop mode skipped" line; otherwise accept.

3. ANSWERS TO THE BRIEF'S QUESTIONS
- Is this the job he asked for? Yes. Two install methods (pip = CLI; installer = app in Applications/Start menu/app menu, started at login, dashboard opened), no signing, no money, no new runtime dependency, Claude Code and MCP independent of the app (verified: skill/MCP never call the server; docs say so in agents.md, getting-started.md, skill). The settled list is respected everywhere I read. The spec corrections recorded in the ledger (install order, ProcessType, stop_tray wait, manifest-less plist) are reflected in the code and architecture.md; I found no spec text that was wrong and built anyway, except that the spec's "install stops the tray" assumes a manifest (F2).
- Is it the simplest thing? Yes for the launcher and login item. The one place it is not the simplest is the open path's assumption "a live tray pidfile means a server is coming" (F1); the simplest correct rule is "a live tray with no server is orphaned: replace it".
- Does it read right to its readers? User docs: yes, the "Two ways to install" table and the ~/Applications clarification are good; F3 is the one ordering problem. Skill files: accurate against the code (exit codes, JSON shapes, `open` has no --json, ~/Applications, tray.log). Claude Code reading SKILL.md gets the right first command (`desktop install --yes --json`). The uninstall copy "resumes from its checkpoint the next time you run it" is a claim I could not verify for dashboard-started jobs (pending owner/lead).
- What would he object to? F1 first ("I clicked the app and nothing happened"), then seeing "Load failed: 5: Input/output error" on his own upgrade (F2), then being told to run `anyscribe ui` when the dashboard is already open (F3).
